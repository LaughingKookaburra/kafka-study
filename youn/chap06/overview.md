# 1. 클러스터 멤버십

- 카프카는 아파치 주키퍼 혹은 Kraft를 사용하여 브로커들의 id를 저장하고 있는다.
- 특정 브로커가 중지되면 Znode는 사라지나 id는 자료구조에 남아있는다. 그래서 동일한 id의 브로커를 다시 등록하면 이전 브로커의 토픽과 파티션들을 할당받는다.

# 2. 컨트롤러
- 컨트롤러는 일반적인 브로커의 기능에 더해서 파티션, 레플리카 중에서 리더를 선출하는 역할을 맡는다.
- 클러스터에서 가장 먼저 시작하는 브로커가 컨트롤러가 된다.
- 컨트롤러가 없어지면 다른 브로커들이 알게되고 컨트롤러가 되려고 시도한다. 

###  2-1. epoch (에포크)
- 컨트롤러 브러커가 오랫동안 연결이 끊겨있는동안 새로운 컨트롤러가 선출될 수 있다.
- 다시 돌아온 브로커는 이 사실을 모르고 메세지를 보낼 수 있기 때문이다.
- 컨트롤러가 선출될 때 마다 epoch가 증가하고 만약 낮은 epoch를 가진 메세지가 온다면 해당 메세지를 무시한다.

### 2-2. KRaft 기반 새로운 컨트롤러

**왜 새롭게 만들었나?**
- 컨트롤러가 재시작 될 때 마다 모든 브로커 정보를 읽고 모든 브로커로 보내야한다. (병목현상이 심함)
- 컨트롤러가 주키퍼에 정보 입력 -> 동기 / 브로커한테 메세지 전송 -> 비동기 / 주키퍼가 컨트롤러한테 정보 업데이트 -> 비동기 이러한 비일관성에 의해 비접합성 발생
- 메타 데이터 관련하여 어떤 작업은 주키퍼가, 어떤 작업은 컨트롤러가 하다보니 아키텍쳐 관점에서 좋지 않다.

기존 주키퍼의 역할은 컨트롤러 선출, 메타데이터 저장을 책임진다.
  
새로운 아키텍쳐는 메타 데이터 정보를 로그화하여 저장한다. (기존 카프카 작동 방식과 유사하고 성능에 이점이 있다.)
- 액티브 컨트롤러 (리더)는 브로커가 보내온 모든 RPC 호출을 처리한다.
- 팔로워 컨트롤러들은 액티브 컨트롤러에 쓰여진 데이터를 복제한다.
- 액티브 컨트롤러에서 장애가 발생한 경우 즉시 투입될 수 있어서 리로드 기간이 거의 없어진다.


일반 브로커들이 액티브 컨트롤러로부터 컨슈머와 같이 정보를 pull하고 컨트롤러들은 브로커들의 컨슘 offset을 관리한다.
   
 
현재 카프카측은 주키퍼에서 KRaft로 이전할 수 있게 브리지 릴리스 기능을 제공해준다.
 
# 3.  복제
- 카프카에 저장되는 데이터는 토픽에 의해 조직화된다.
- 토픽은 1개 이상의 파티션으로 분할된다.
- 파티션은 다수의 레플리카를 가질 수 있다.

레플리카에는 2종류가 있다.
- 리더 레플리카 : 모든 쓰기 요청은 리더 레플리카한테로만 간다. (읽기도 가능)
- 팔로워 레플리카 : 리더 레플리카의 데이터를 복제하여 최신 상태를 유지하고 리더 레플리카의 대체 준비를 한다. (읽기 가능)

이 두 레플리카의 통신 메커니즘은
- 팔로워 레플리카가 리더 레플리카에게 읽기 요청을 보낸다. (컨슈머가 메세지 읽을 때 사용하는 요청과 동일)
- 요청을 보낼 때 다음번에 받아야 할 메세지 오프셋도 넘긴다. (어디까지 했는지를 알려준다.)
- 리더 레플리카는 팔로워들의 메세지 트래킹 여부를 알 수 있다.
- replica.leg.time.max.ms 설정을 통해 리더 - 팔로워 레플리카의 동기화 풀림 판단 최대 시간을 판단한다.


# 4 요청 처리
### 4.1 요청처리 메커니즘
- 브로커는 연결을 받는 포트별로 acceptor 스레드를 생성한다.
- acceptor 스레드는 들어온 요청을 네트워크 스레드에게 넘긴다. (네트워크 스레드 수 조정 가능)
- 네으워크 스레드들은 요청 큐에 요청을 넣는다.
- I/O 스레드들은 요청 큐에서 요청을 가져와 처리하고 완료되면 응답 큐에 넣는다.

### 4.2 요청의 종류
- 쓰기 요청 - 프로듀서가 보내는 메세지 쓰기 요청
- 읽기 요청 - 컨슈머, 팔로워 레플리카가가 보낸 요청
- 어드민 요청 - 토픽 생성, 삭제 등의 메타데이터 작업 수행중인 어드민 클라이언트가 보낸 요청

### 4.3 요청 
- 리더 레플리케이션이 아닌 레플케이션에 요청을 보내서는 안된다.
- 클라이언트는 메터데이터 요청을 통해 어느 레플리케이션에 요청을 보내야 하는지 알 수 있다.
- 클라이언트는 보통 이 정보를 캐싱하고 있다.
- 만약 레플리케이션 사이에 변경이 생겨 캐싱 정보로 요청을 보냈을 때 오류를 반환받으면 그 때 메타데이터를 새로고침한다.

### 4.4 쓰기 요청
- ack=1, ack=0, ack=all 로 설정이 나누어진다.
- 리더 레플리카가 클라이언트로부터 요청을 받게되면 몇 가지 유효성 검증을 한다.
  - 클라이언트가 토픽에 대한 쓰기 권한이 있는가.
  - ack의 설정값이 올바른가?
  - ack=all 이면 인-싱크 레플리카가 있는가
- 검증 후 새 메세지들을 로컬 디스크에 쓴다.
- 리눅스의 경우 파일시스템 캐시에 작성한다.
- ack=0,1이면 리더가 메세지를 쓰고나서 바로 응답을 보낸다.
- ack=all이면 퍼커토리라는 버퍼에 저장하고 팔로워들이 모두 복제를 하면 클라이언트에게 응답을 보낸다.

### 4.5 읽기 요청
- 클라이언트는 토픽, 파티션, 오프셋 정보를 보내면서 이에 해당하는 메세지를 요구한다.
- 브로커는 컨슈머가 지정한 크기 한도만큼 메세지를 보내준다.
- 메세지를 보낼 때 제로 최적화를 적용한다.
- 제로 카피란 파일 시스템에서 읽은 데이터를 중간 버퍼에 넣지 않고 바로 네트워크 채널로 보내는 것을 의미한다.
- 보내는 데이터 양의 하한도 정의함으로 네트워크 오버헤드를 줄일 수 있다.
- 대부분의 클라이언트들(컨슈머)은 인 싱크 레플리케이션으로부터만 데이터를 읽을 수 있다.

# 5. 물리적 저장소
- 카프카의 기본 저장 단위는 파티션 레플리카이다.
- 파티션은 서로 다른 브로커들 사이에 분리되어 저장될 수 없고 서로 다른 디스크에도 분할 저장을 할 수 없다.

### 5.1 계층화된 저장소
- 계층화던 저장소 기능은 클러스터의 저장소를 로컬, 원격 2가지로 나눈다.
- 로컬 계층은 로그 세그먼트를 저장하기 위해 브로커의 로컬 디스크를 사용한다.
- 원격 계층은 로그 세그먼트를 저장하기 위해 HDFS, S3에 저장한다.
- 네트워크 계층을 사용함으로 오래된 데이터를 읽을 때 네트워크에서 바로 읽어올 수 있다.
- 이는 Disk I/O, 로컬 읽기와 페이지 캐싱들을 두고 경합할 필요가 없어진다.

### 5.2 파티션 할당
- 레플리카들을 가능한 브로커 간에 고르게 분산시킨다.
- 한 파티션에 대한 각각의 레플리카들은 서로 다른 브로커에 배치되도록한다.
- 브로커의 랙 정보가 설정되어 있다면 각각의 파티션 레플리카들을 서로 다른 렉에 할당한다.

### 5.3 파일 관리
- 카프카는 영구히 데이터를 저장하지 않는다.
- 데이터를 지우기전에 모든 컨슈머가 읽어갈 수 있도록 기다리지도 않는다.
- 보존 기간을 설정할 수 있다.
- 하나의 파티션은 여러개의 세그먼트로 나누어진다.
- 1GB 혹은 1주일치 데이터가 쌓인다고 하면 세그먼트를 저장한다.
- 현재 작성중인 세그먼트는 액티브 세그먼트라고 한다.

### 5.4 파일 형식
- 저장하는 파일에는 카프카 메세지, 오프셋이 저장된다.
- 데이터의 형식은 프로듀서가 보내는, 컨슈머한테 보내는 파일 형식과 일치한다.
- 이를 통해 네트워크, 디스크 작업시 압축을 2번할 필요도 없고 제로 카피가 가능해진다.
- 메세지 배치 헤더에는 여러가지 값이 있는데 대표적으로
  - 메세지 현재 형식의 버전
  - 배치에 포함된 첫 번째 메세지 오프셋과 마지막 오프셋 차이
  - 첫 번째 메세지의 타임스탬프, 가장 큰 타임 스탬프
  - 배치 크기

### 5.5 인덱스
- 카프카는 컨슈머가 임의의 오프셋부터 메세지를 읽어올 수 있도록 한다.
- 이를 위해 각 파티션 별로 인덱스를 유지한다.
- 해당 인덱스는 오프셋과 세그먼트 파일 및 파일 내에서 위치를 맵핑하고 있다.

### 5.6 압착
- 고객의 배송지 주소를 저장'만'하는데 카프카를 사용한다고 생각해보자.
- 만약 이런 경우 이전 데이터를 저장할 필요없이 최근 데이터만 저장해도 된다. 
- 각 키의 최근 값만 저장하는 기능을 지원해준다.
- 이 기능을 위해 로그는 '클린', '더티' 두 가지 영역으로 나누어진다.
- 클린 - 압착된 적이 있던 메세지들이 저장된다.
- 더티 - 마지막 압착 작업 이후 쓰여진 메세지들이 저장된다.
- 브로커는 압착 매니저 스레드와 압착 스레드 여러개를 실행시킨다.
  - 파티션의 더티 영역을 읽어서 인메모리 맵을 생성한다.
  - 클린 세그먼트들을 오래된 것 부터 읽으면서 오프셋 맵의 내용과 대조한다.
  - 그렇게 클린 세그먼트들을 갱신한다.


### 5.7 삭제
- 특정 키의 최근 메세지만 저장된다면 해당 키를 삭제하려면?
- 해당 키에 value가 null인 메세지를 써주면 된다.

### 5.8 압착 타이밍
- 기본적으로 카프카는 토픽 내용물의 50% 이상이 더티 레코드이면 압착을 시작한다.
- min.compaction.log.ms - 메세지가 쓰여진 뒤 압착될 때까지 지나가야하는 최소 시간
- max.compaction.lag.ms - 메세지가 쓰여진 후 압착이 가능해질 때까지 딜레이 될 수 있는 최대 시간
